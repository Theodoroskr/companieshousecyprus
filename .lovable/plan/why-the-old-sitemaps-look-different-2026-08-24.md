# Why the old sitemaps look different

## What Search Console is showing

Two generations of sitemaps are listed side by side:

| Entry | Where it came from | State |
| --- | --- | --- |
| `/sitemap.xml` (Sitemap index, submitted 24 Aug 2026) | The current app | Success |
| `/new_company_sitemap_2..10.xml` (submitted 4 Jul 2025) | The old WordPress site | "Couldn't fetch" |

The nine `new_company_sitemap_*.xml` files were generated by the WordPress plugin that used to run the site. They were split into 15,000-URL chunks, which is why each row reports "Discovered pages 15,000" — that number is the count Google remembers from the last time it *successfully* read the file in 2025, not a current count.

Those URLs no longer exist. The new app serves a different structure:

```text
/sitemap.xml                      -> sitemap index
  /sitemaps/pages.xml             -> static pages (home, search, solutions, contact, ...)
  /sitemaps/companies/0.xml       -> company profiles, 50,000 URLs per chunk
  /sitemaps/companies/1.xml
  ...
```

Verified against the running app: `/sitemap.xml`, `/sitemaps/pages.xml` and `/sitemaps/companies/0.xml` all return valid XML, and `/new_company_sitemap_2.xml` returns 404. So "Couldn't fetch" is the correct and expected result for the legacy rows — nothing is broken.

The new index showing "Discovered pages 0" is also normal for a sitemap submitted the same day: Google records the index first and reads the child sitemaps over the following days.

## What to do about it

1. Remove the nine `new_company_sitemap_*.xml` entries in Search Console (Indexing -> Sitemaps -> open each row -> Remove sitemap). They are stale submissions from the old platform; only the owner can delete them, code changes cannot. Keeping them does not harm rankings, but it leaves permanent red rows in the report.
2. Leave `/sitemap.xml` as the only submitted sitemap and let Google work through the chunks.

## Optional code follow-up

If you would rather Google retire the old URLs faster than waiting for the 404s to age out, add a small route that answers the nine legacy paths with HTTP 410 Gone instead of the app's 404 page. 410 is a stronger "permanently removed" signal than 404 and takes those rows out of the report sooner.

Nothing else in the sitemap setup needs changing.
